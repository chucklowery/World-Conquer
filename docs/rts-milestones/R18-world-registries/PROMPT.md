# R18 — Dynamic RTS world, house and gameplay-definition registries

Implement **R18** in `https://github.com/chucklowery/World-Conquer` on a clean branch from the latest integration branch. **This is a standalone implementation prompt; no earlier conversation is required.** R00 is completed: `browser/engine/simulation_contract.h` exposes stable contract IDs, commands, events, ticks and JSON snapshots of *Courier Extraction*. It still projects four fixed infantry IDs, two crate IDs, one extraction ID, an 18×11 map and hard-coded owner/team assignments from `courier::State`; combat/sentries/objectives remain Courier-specific. R05 is completed as an independent, deterministic two-faction art pack under `game/content/r05/`, whose `r05.*` keys are **visual asset IDs, not entity IDs or gameplay rules**. Read `docs/browser/ARCHITECTURE.md`, `docs/browser/R05_ORIGINAL_FACTIONS.md`, `docs/rts-milestones/REVIEW-R00-R05.md`, `browser/engine/README.md`, and the current host/browser tests before designing a replacement.

**Dependency gate:** both **R00 and R05** must be `completed` in `docs/rts-milestones/MANIFEST.md` and integrated. If not, mark this milestone `blocked`. R01 may run independently. **R02/R03/R04 must wait for R18**, so they extend one native world/registry rather than each inventing an incompatible one.

**Deliverable:** a production-oriented **native C++** RTS world/registry layer behind the accepted R00 command/event/snapshot boundary, supporting multiple dynamic houses and teams, faction/neutral identity, immutable gameplay-definition IDs separate from stable **instance** entity IDs and `r05.*` asset keys, spawn/despawn/restart lifecycles, and configurable map dimensions. Define canonical ownership of house state and entity state, allocation/epoch/serialization conventions for deterministic replay and multiplayer, and a versioned content-definition schema with validated role/faction/footprint/visual-key mappings. The small initial catalog can bind Aster and Forge roles to R05 visuals without implementing harvesting, production, power, weapons or finished drawing here. Reserve explicit extension seams for R02 pathing, R03 combat, R04 maps, R06 economy, R07 structures, R08 tech, R09 visibility and R14 saves. Keep the engine's actual `InfantryClass::AI`/`MapClass` movement authoritative in Courier mode; retain the current mode and native browser compatibility as an adapter, not a competing JavaScript simulation.

**Contract requirements:** define which IDs persist across ticks vs match restarts, how simultaneous spawns obtain deterministic IDs, how dead/despawned entities and unselected state appear in snapshots, how command issuer/ownership and house-team membership are validated, and how entity creation/removal events are ordered. Reject duplicate/replayed command sequences **even after earlier orders have executed**, inconsistent definition/art references, invalid house/team references and malformed dynamic maps without mutating the world. Provide explicit, backward-compatible schema migration or negotiated version rejection for R00 v1 snapshots and existing consumers. Bound command queues, event retention and entity counts to a documented budget; do not introduce hidden JS authority.

**Acceptance:** native host tests cover two houses plus neutral entities; variable map sizes; deterministic mixed spawn/order/despawn and restart; ID reuse/epoch policy; correct owner/team isolation; absent selection; invalid/stale/replayed commands; safe malformed definition rejection; snapshot version and C++→JS event parity. Run the **real compiled WebAssembly** Courier mission from start through win/loss/restart and assert live `InfantryClass` movement matches its HUD snapshot. Show a second small native-world fixture with dynamic actors and both faction definition keys visible in versioned snapshots **without pretending they are yet production/harvesting systems**. Document the schema, ownership/lifecycle API and compatibility policy in `docs/browser/ARCHITECTURE.md`, with migration tests on the `simulation-bridge.js` consumer. Existing R00/R05 tests and relevant Linux/macOS/Windows/MinGW/browser CI must stay green.

**Manifest protocol:** edit **only R18's row** in `docs/rts-milestones/MANIFEST.md`: `in_progress` when starting, `blocked` with concrete reason if gated, and `completed` only after host/Node/WASM/Chromium acceptance and relevant GitHub Actions are verified. Preserve the original R00 and R05 `completed` rows and all other statuses/evidence. Record PR, SHA, exact commands/results, CI links and browser observation, run `node docs/rts-milestones/validate-roadmap.js` and workflow checks, and create a scoped PR. Do not use proprietary game assets or silently rewrite historical VanillaTD game modes.
