# M1: The stock VanillaTD engine runs in the browser (single-session plan)

Read `docs/milestones/AGENT_GUIDE.md` first. This file is self-contained apart
from that guide, and is designed to be **completed in one long agent session**
on **one branch** with **one PR**.

## Goal

The unmodified VanillaTD game loop (`main()` with no `--browser-*` flag)
boots in Chromium on **original placeholder data** generated by this
milestone. It reaches the **main menu** and responds to mouse and keyboard,
never freezes the tab, reports missing files precisely, and is checked by a
new `stock-engine` CI job.

Starting and playing a scenario is **not** part of M1. It needs terrain,
units and a scenario file, which M2 produces; M2's end-to-end phase
extends this milestone's CI job to cover it.

## Session contract (read before starting)

1. **One branch, one PR.** Create `m1/stock-engine-in-browser` from the
   latest `vanilla`. Open a **draft PR** after Phase 1 and push after every
   phase, so the work survives a session interruption. Mark it ready at the
   end.
2. **Keep a session log.** Create `docs/browser/M1_SESSION_LOG.md` in
   Phase 0. After each phase, append: phase number, status (done, partial,
   skipped), commit SHA, commands run with results, and open issues. If your
   context is reset or you resume later, **read this log first** and continue
   from the first phase not marked done.
3. **Commit at every phase boundary**, with message
   `M1 phase <n>: <summary>`. Keep each commit buildable.
4. **Work through the phases in order without stopping to ask.** Use the
   stated defaults for every decision. Stop and ask only for the "Stop and
   ask" cases in AGENT_GUIDE.md section 2, or when this file says **STOP**.
5. **Time-box.** Each phase has a soft budget. If you exceed about twice
   that budget without progress, apply the phase's fallback, record it in
   the log, and move on. Do not let one phase consume the session.
6. **Verify locally before relying on CI.** Install emsdk 3.1.68 in
   Phase 0 and rebuild the WASM target after every engine change. A full
   rebuild is slow, so batch related C++ edits and rebuild once per batch.
7. **Never bypass the engine.** Do not draw a fake menu, skip `Main_Menu`,
   or add a `--browser-*` shortcut to satisfy the gate. The gate is about the
   stock path.

## Current state (verify in Phase 0)

- `vanillatd.{html,js,wasm}` builds with `-sASYNCIFY=1`, `-sINVOKE_RUN=0`,
  `-sFORCE_FILESYSTEM=1` and `-sALLOW_MEMORY_GROWTH=1`
  (`tiberiandawn/CMakeLists.txt`, `if(EMSCRIPTEN)` block).
- Asyncify yields in `Call_Back()`, `Frame_Limiter()` (`common/framelimit.cpp`)
  and `ms_sleep`/`us_sleep` (`common/mssleep.h`). See ADR-0002 in
  `docs/browser/DECISIONS.md`.
- `browser/engine/shell.html`: the first panel is the stock engine, and
  **Launch experimental game** runs `Module.callMain([])` after
  `asset-import.js` copies user-selected files into MEMFS at `/game`.
- `tiberiandawn/init.cpp` prints `[browser-game] menu.enter`,
  `menu.choice=N`, `scenario.request=…`, `scenario.loaded=…` and
  `scenario.failed=…`. Startup MIX registration is in the same file
  (`CCLOCAL.MIX`/`LOCAL.MIX`, `CONQUER.MIX`, `GENERAL.MIX`, `SOUNDS.MIX`, …).
- `tools/content/encode-shape.js` (SHP) and `encode-palette.js` (PAL) exist.
  `tools/mixtool` builds MIX archives (native, `-DBUILD_TOOLS=ON`).

## Phase 0: Setup and baseline

1. Branch `m1/stock-engine-in-browser` from `vanilla`.
2. Install emsdk 3.1.68, Ninja, Node 18+ and (for mixtool)
   `libsdl2-dev libopenal-dev`.
3. Build the WASM target with the command in AGENT_GUIDE.md section 3, and
   the native tools build with `-DBUILD_TOOLS=ON`. Confirm that
   `build/native/tools/mixtool/` contains a `makemix`-style binary (find its
   exact name) and that `--help` runs.
4. Run `node docs/rts-milestones/validate-roadmap.js` and
   `bash scripts/check-rts-foundation.sh`. Both must pass before you change
   anything.
5. Install Playwright locally the way `.github/workflows/browser-engine.yml`
   does, and run `node browser/engine/check-runtime.js` once against your
   local build to confirm that the existing browser suite passes.
6. Create `docs/browser/M1_SESSION_LOG.md` with the toolchain versions and
   baseline results.

**Fallback:** if the existing browser suite fails on unchanged `vanilla`,
record it in the log, then continue; do not fix legacy demos.

## Phase 1: Asset audit log and visible fatal errors

1. Add a CMake option `WC_ASSET_AUDIT`, default **ON for Emscripten** and
   OFF for native builds. It defines a macro that enables logging of one line
   per lookup outcome:
   - `[asset-hit] <NAME> <loose|MIXNAME>` (once per name)
   - `[asset-miss] <NAME>` (every time)

   Hook the real lookup layer: the CD/MIX-aware file class used by
   `CCFileClass` (`Is_Available`/`Open`) and MIX retrieval
   (`MixFileClass::Offset`/`Retrieve` in `common/mixfile.h`, used by
   `MFCD::Retrieve`). Prefer one hook point in `common/` over many call
   sites.
2. In browser builds, every startup path that aborts for missing data
   (search `init.cpp` and `startup.cpp` for `Prog_End`, `exit(`, and returns
   after failed `MFCD` or file checks) prints
   `[browser-game] fatal=<short reason>` first.
3. In `shell.html`, parse those lines from Emscripten `print`/`printErr`
   into `window.WCAssetAudit = {hits:[], misses:[], fatal:null}`. Show
   `fatal` in the status line in red.
4. Add a Node unit test for the parser (`browser/engine/test-asset-audit.js`).
5. Rebuild native with `-DWC_ASSET_AUDIT=ON` and `OFF` to prove both
   compile.
6. Commit, push, and open the **draft PR**.

## Phase 2: Empty-data run and boot-path inventory

1. With an **empty** `/game`, run the stock engine in headless Chromium
   (write a throwaway Playwright script or start `check-stock-engine.js`
   early). Capture all `[asset-miss]` lines and the `fatal=` reason.
2. Statically list every file the boot → menu path can request: string
   literals ending in `.MIX`, `.PAL`, `.SHP`, `.CPS`, `.FNT`, `.ENG` and
   `.INI` in `tiberiandawn/init.cpp`, `startup.cpp`, `conquer.cpp`,
   `menus.cpp`, `dialog.cpp`, the mouse and font setup, and names built with
   `sprintf`/`Language_Name`.
3. Write `game/content/pack/boot-requirements.json`: entries of
   `{name, container, format, requiredFor:"boot"|"menu"|"optional",
   referencedAt:["file:line"], contract:{…}}`. Every contract value (size,
   frame count, entry count) needs the code location that proves it; mark
   unknown values `"unverified"`. M2 will extend this file to the full game.
4. Record the empty-data result and inventory summary in
   `docs/browser/M1_PLATFORM_AUDIT.md`.

## Phase 3: Blocking-loop audit and watchdog

1. Add a **watchdog** to `shell.html`: a `requestAnimationFrame` heartbeat
   that logs `[browser-watchdog] stall=<ms>` whenever the gap exceeds 250 ms
   and keeps the maximum in `window.WCWatchdog.maxStallMs`.
2. List the loops on the boot → menu → dialog path that might not yield:
   `Select_Game`, `Main_Menu`, intro and `Play_Movie`, palette fades
   (`Fade_Palette_To`), `Delay`/countdown waits, `Keyboard->Check`/`Get_Key`
   waits, message boxes (`msgbox.cpp`), option and load dialogs
   (`goptions.cpp`, `loaddlg.cpp`, `gamedlg.cpp`), and VQA playback
   (`common/vqa*.cpp`). Search for `while (`, `for (;;)`, `do {`,
   `TickCount` and `Delay(`.
3. For each loop, decide whether every iteration reaches `Call_Back()`,
   `Frame_Limiter()` or a sleep. Where one doesn't, add a yield, preferably
   inside a shared helper, under `#ifdef __EMSCRIPTEN__`.
4. Make missing movies return immediately from `Play_Movie` in browser
   builds if they don't already.
5. Record a table of loop, file:line, yields (yes/no), and fix applied, in
   `M1_PLATFORM_AUDIT.md`. The scenario-time path (`Main_Loop`) is in scope
   for review but cannot be exercised until M2; mark those rows "reviewed,
   unexercised".
6. Rebuild and confirm the existing `--browser-cooperative-probe` check
   still passes.

**Fallback:** if a loop needs a structural rewrite, don't do it. Add a
TODO row with the reason, and continue.

## Phase 4: Data pack loader and settings persistence

1. Pack manifest (this milestone defines it; M2 produces full packs):
   `pack.json` = `{schema:1, packVersion:string, files:[{path, bytes, sha256}]}`.
   `path` is relative to `/game`, uppercase, `[A-Z0-9_.-]` per segment, with
   optional lowercase `gdi/`, `nod/` or `covertops/` directories, and no
   `..` or absolute paths.
2. Add `browser/engine/pack-loader.js`. It fetches `data/pack.json`, then
   each file, verifies the size and SHA-256 (Web Crypto), writes the file to
   MEMFS before `callMain`, and reports progress. Any mismatch is fatal and
   names the file.
3. Cache files with the Cache API keyed by `packVersion`. Wrap all storage
   calls in try/catch; loading must work without the cache.
4. Persist `/game/user` with IDBFS: mount it before `main()`, run
   `FS.syncfs(true)` on load and `FS.syncfs(false)` after the engine writes,
   on a timer and on `visibilitychange`. Default to IDBFS; OPFS is a later
   option.
5. In `shell.html`'s stock engine panel, **Play** loads `data/pack.json` when
   it is served and launches the engine. If no pack is served, the existing
   local file import and **Launch experimental game** path remains.
6. Add Node tests (`browser/engine/test-pack-loader.js`) for manifest
   validation, hash mismatch, a missing file, and illegal paths.
7. Copy `pack-loader.js` in the workflow staging step, next to the other
   runtime scripts.

## Phase 5: Boot placeholder pack generator

**Purpose:** the smallest set of **original, generated** files that lets the
stock engine reach its main menu. Ugly is fine: flat colors and simple
bitmap glyphs. M2 absorbs this generator into its full pack pipeline.

1. Add `tools/content/boot-pack.js build <outDir>`. Driven by
   `boot-requirements.json`, it writes `<outDir>/game/…` (loose files and
   MIX archives), `<outDir>/pack.json` (Phase 4 format) and
   `<outDir>/PROVENANCE.json` (each file: generator, `license: "CC0-1.0"`,
   source revision). The output must be byte-for-byte deterministic.
2. Encoders: reuse `encode-palette.js` and `encode-shape.js`. Write new
   ones only for formats on the boot path, each with a round-trip test
   against the engine's real decoder via a small host C++ harness (pattern:
   `tests/test-original-shape.cpp`):
   - **FNT** fonts: read `common/font.cpp`. Generate fixed-width glyphs
     from a small hand-written bitmap table in the script.
   - **CPS/LCW pictures**, if the menu loads any: read `common/iff.cpp`
     (`Load_Uncompress`/`Load_Picture`) and `common/lcw.cpp`.
   - **String table** (`CONQUER.ENG` via `Language_Name("CONQUER")`):
     read how `SystemStrings` and `Text_String()` index it
     (`tiberiandawn/init.cpp`, `function.h`). Generate it from the `TXT_*`
     enum, so every index exists. Use original wording; no EA trademarks.
     The houses are **Aster** and **Forge**.
3. MIX archives: build them with the native mixtool (Phase 0). Verify
   with its `--list` mode that each archive contains the expected names.
4. Add the generator to CI: in `browser-engine.yml`, build the native
   mixtool, run `boot-pack.js`, and stage the output under
   `build/browser-engine/data/`. Upload it as artifact
   `world-conquer-boot-pack`. **Never commit generated binaries**; the
   generator and its sources are what's committed.
5. Node tests (`tools/content/test-boot-pack.js`) check determinism (build
   twice and compare `pack.json`), manifest/provenance completeness, and
   that every `boot`/`menu` entry in `boot-requirements.json` has an
   output.

**Fallback:** if a required boot format can't be determined from the code
within the time-box, emit the smallest structurally valid file you can
justify from the loader, mark that entry `"contract":"minimal-unverified"`,
and let Phase 6 prove or disprove it.

## Phase 6: Reach the main menu

1. Serve `build/browser-engine` with the boot pack under `data/`, click
   **Play**, and iterate: read `[asset-miss]`/`fatal=` → extend the inventory
   and the generator → rebuild the pack → retry. Rebuild WASM only when you
   change engine code.
2. If startup aborts because an **optional** archive is absent (movies,
   scores, speech), make that path tolerant in browser builds with a minimal
   guarded change. Do not generate fake versions of EA archive contents.
3. Done when `[browser-game] menu.enter` appears, the canvas shows the menu
   (screenshot not blank), the mouse cursor moves, and clicking or pressing
   keys changes the menu selection, with `WCWatchdog.maxStallMs` below 1,000
   after startup.
4. Exercise each top-level menu entry that does not need scenario data
   (options dialog, exit or cancel paths). Confirm each opens, renders and
   closes without a stall or fatal error. Entries that start a game will fail
   for lack of scenario data, which is expected: record the `[asset-miss]`
   lines they produce in `boot-requirements.json` as `requiredFor:"scenario"`.
   They are M2's starting list.

**STOP condition:** if after implementing the PAL, SHP, FNT, CPS and string
encoders the engine still cannot reach `menu.enter` because of a format or
engine behavior you cannot determine, stop Phase 6. Record the exact blocker
(file, loader, code location, what you tried) in the log and the PR, then
continue with Phases 7–9 using the **furthest stage reached** as the CI
assertion, and report M1 as **partial**.

## Phase 7: Display and input

1. Find how the engine sizes its SDL window and back buffer (SDL video code
   in `common/`, plus `Settings` resolution). Scale the canvas to the panel
   width with a correct aspect ratio and `image-rendering: pixelated`, and
   support `devicePixelRatio`. Verify that mouse coordinates map correctly at
   three sizes: narrow (480 px), default, and wide (1600 px).
2. Suppress the context menu on the canvas, prevent page scrolling from
   arrow keys and space while the canvas has focus, and focus the canvas on
   click.
3. On `visibilitychange` to hidden, pause or slow the engine if it exposes a
   pause, otherwise just stop audio-related work; record which.
4. Edge scrolling: the engine scrolls the map when the mouse sits at the
   screen edge, but the pointer can leave the canvas before reaching that
   edge. Make sure the engine sees the pointer at the border (for example by
   clamping the last position reported to SDL when the pointer exits the
   canvas). Add an opt-in pointer-lock toggle button as well; default to no
   pointer lock. Map scrolling itself is verified in M2, once a scenario
   exists.
5. Add these checks to `check-stock-engine.js` (Phase 8): the menu responds
   to a click at a known button position at each of the three sizes.

## Phase 8: `stock-engine` CI job and metrics

1. Write `browser/engine/check-stock-engine.js`. It serves the build with
   `data/`, clicks **Play**, waits for `menu.enter`, takes screenshots
   (pre-launch, menu, after an input), asserts the menu frame is not blank
   and that input changes the frame, and runs the Phase 7 size checks. It
   fails on any page error, any `fatal=`, any `[asset-miss]` for a
   `boot`/`menu` entry, or `maxStallMs > 1000` after startup.
2. Collect metrics into `stock-engine-metrics.json`: `.wasm`/`.js` sizes
   (raw and gzip), the time from navigation to `menu.enter`, the frame-time
   p50/p95 over 30 s at the menu, and `HEAPU8.length` at the menu and 60 s
   later. **No budgets are enforced.**
3. Add a job named **`stock-engine`** to
   `.github/workflows/browser-engine.yml` (same toolchain setup; it can reuse
   the build through an artifact or rebuild). Run it on every PR and push.
   Upload the screenshots, metrics and audit log as artifacts.
4. Push, and make sure the PR's `stock-engine` job and all existing
   browser, legacy-demo and native **build** jobs are green. (The known
   `publish-release` asset-limit failure is not yours.)

## Phase 9: Owner checklist, docs and roadmap evidence

1. Write `docs/browser/M1_OWNER_CHECK.md`, steps for the owner to run
   locally with a legally owned TD installation: serve the build, use
   **Choose folder**, click **Launch experimental game**, reach the menu,
   start mission 1, and play 2 minutes. Then record browser and version,
   commit SHA, and the miss list (file names only). Do not include EA
   screenshots in the repo. You do not run this yourself.
2. Update `docs/browser/BUILD.md` (how to build and serve with the boot
   pack) and `browser/engine/README.md` (the **Play** button and pack loader).
3. In `docs/ROADMAP.md`, tick the M1 checkboxes you completed, tick the M0
   item "stock-engine headless smoke test", and add the evidence line under
   M1:
   `Evidence: <date> · <SHA> · <stock-engine CI run> · Chromium <version> · menu reached on original boot pack; input responsive; max stall <n> ms`.
   If Phase 6 hit its STOP condition, add the line with "partial: <furthest
   stage>" instead, and leave the exit-gate checkbox unticked.
4. Finish the session log, mark the PR ready for review, and post the final
   report (AGENT_GUIDE.md section 6), listing every phase's status.

## M1 exit gate

On the PR's head commit (and later on `vanilla`), the `stock-engine` CI job
passes and shows that the unmodified engine `main()` in Chromium:

1. loads the generated, original boot pack through `pack-loader.js`, with
   hashes verified;
2. reaches `[browser-game] menu.enter` and renders the menu with the engine's
   own renderer;
3. responds to mouse and keyboard at three canvas sizes;
4. has zero page errors, zero `fatal=` lines, zero boot/menu asset misses,
   and a maximum stall of 1,000 ms or less after startup;
5. publishes `stock-engine-metrics.json`.

The existing browser suite, the legacy demo regression, and the native
build jobs stay green.

## Handed to M2

- `boot-requirements.json`, including `requiredFor:"scenario"` entries
  observed in Phase 6 → becomes M2's `requirements.json`.
- `boot-pack.js` and its encoders → absorbed into M2's pack pipeline (`tools/content/pack.js`).
- `check-stock-engine.js` → shared with M2's `check-stock-scenario.js`, which starts a match and plays.
- Loops marked "reviewed, unexercised" → verified when a scenario runs.

## Out of scope for M1

Starting or playing a scenario, real art, audio (M4), saves (M4), Asyncify
removal, mobile/touch, multiplayer, and any change to the frozen legacy
demos beyond keeping their tests green.
